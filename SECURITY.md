# Security Policy

## Reporting a vulnerability

Please report security issues privately through
[GitHub Security Advisories](https://github.com/Beeeeen/krinos/security/advisories/new).

Do not open a public issue for a vulnerability.

**What to expect:**

| | |
| --- | --- |
| Acknowledgement | within 3 working days |
| Initial assessment | within 10 working days |
| Fix or mitigation plan | communicated with the assessment |
| Public disclosure | coordinated with you, default 90 days |

We will credit you in the advisory unless you ask us not to. We do not
currently run a paid bounty.

## What we consider a vulnerability in Krinos

Krinos reads untrusted input — scanner reports are generated by tools running
over arbitrary repositories — and writes to CI logs. That shapes the threat
model:

**In scope:**

- **A secret value reaching our output.** Krinos writes to build logs and
  artifacts. If any adapter or renderer copies a credential out of a scanner
  report into a report of ours, that is a vulnerability, not a bug. We treat
  it as our highest severity class.
- **Crashes or resource exhaustion on malformed input.** A crafted report that
  panics Krinos, or drives it to unbounded memory or CPU, breaks the pipeline
  it was installed to protect.
- **Path traversal or unintended filesystem access** from a crafted report.
- **A finding being silently dropped.** If a report can be crafted so that a
  real finding disappears from the output entirely — not suppressed with a
  reason, but absent — that is a security issue. It turns us into a tool that
  hides vulnerabilities.
- Anything in the release or build pipeline that could let a third party ship
  a binary as us.

**Not in scope:**

- **Disagreement with a verdict.** Krinos deciding something is `suppress`
  when you believe it is `act` is a tuning issue. Open a normal issue with the
  finding and the evidence we printed — we want those, they are how the engine
  improves, but they are not security reports.
- Vulnerabilities in the scanners whose output we read. Report those upstream.
- Vulnerabilities in a repository you scanned. That is the point of the tool.

## Supported versions

Pre-1.0, only the latest minor release receives security fixes. After 1.0 we
will support the current and previous minor release.

## Our own supply chain

Krinos has zero third-party dependencies, and CI fails the build if that
changes. Release binaries are built from a pinned Go toolchain with
`-trimpath`, and the container image is `scratch`-based with no shell and no
OS packages.

If you find a way to weaken any of that, we would very much like to hear about
it.
